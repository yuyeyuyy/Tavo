## 2026-11-16：从前后端理解 Session Agent

| Agent 概念 | 熟悉的前后端类比 | 需要区分的地方 |
| --- | --- | --- |
| Session / Message | 会话主表和有类型的子表 | 对话 Session 不是登录 Token |
| UserMessage / AssistantMessage | 用户提交和服务端生成的记录 | 客户端只能提交用户内容，不能伪造模型角色 |
| Tool / ToolCall / ToolResult | Service 方法 / 调用请求 / 返回值 | 模型只能提议，后端校验和执行，结果独立持久化 |
| Reviewer / Decision | 权限拦截器 / 审计记录 | 模型不能批准自己，人工也不能扩大工具白名单 |
| Context | 本轮发给模型的请求 DTO | 历史持久化不代表全量发送，也不代表长期记忆 |
| Assistant / Run | 应用服务 / 持久任务实例 | 同一用户消息可显式重试成新Run，保留关联而不复制用户消息 |

方案比较：无状态内存循环短小，但重启丢审核、难以识别未知付费请求；持久 Session/Run 多一些状态建模，换来幂等、恢复和审计。本轮选后者，并复用现有 LangGraph/Worker。安全判断比较模型自审与确定性规则，选规则权威+可选人工确认。

最重要的边界：前端 abort 只是停止等待；取消必须写后端 Run。模型请求前记录 inflight，响应丢失后不盲重发。lease/fence 像数据库写版本，旧 Worker 不能提交；线程超时不代表线程已停止，所以资源名额继续保留。Context 只裁剪完整旧轮次，不能留下没有结果的工具调用。

小练习：画出“12÷3 → calculate → ask → 用户拒绝 → denied ToolResult → 模型解释”的状态图。说明为何不能把拒绝记成0、不能由客户端POST成功ToolResult，以及断网后应查询哪个Session/Run ID。进阶：找出 `assistant.py` 中模型请求前后的两次事务，解释为何网络等待不能放在SQLite写事务里。


## 2026-11-16：AgentPool、模型自审查和Bash

Pool类似Web服务的并发请求执行器，持久任务队列仍在数据库；线程池只是读取工具的一种执行方式。提取Pool统一所有权和资源名额，避免超时后“字典里没任务、外部进程却仍在跑”。

比较直接宿主shell和隔离容器，采用后者；比较主模型自称安全和独立无工具复核，采用后者，并由规则收紧决定。复核是额外的模型请求，会产生延迟和费用；权限来自明确启用的沙箱能力与后端约束。Mock决策也能触发真实沙箱命令，界面必须说明。

工具失败不是空结果：非零退出/OOM/超时/拒绝分别记录，结果未知不能自动重跑写命令。SQLite fence像写版本，只拒绝旧提交，无法撤销已经写入Docker卷的文件。工作卷持久化独立于数据库，需要单独备份；单文件上限不等于卷总容量配额。

小练习：画出“命令写入完成→结果尚未提交→进程崩溃”的时间线，解释恢复为何不能直接重放。再解释旧Worker关闭为何只能处理自己owner/fence的容器，以及把工具stdout当授权指令会出现什么问题。

## 2026-11-16：启动准备与运行时检查

Docker CLI是客户端，daemon才负责容器；命令存在不代表服务已启动。检查镜像也不代表镜像中Bash能在限制条件下运行，因此启动会实际创建、执行并清理一个短命容器，再让后端就绪。默认镜像缺失自动构建，自定义镜像缺失拒绝替换；构建超时/日志和预热都有上限。

两种方案：常驻容器配合`docker exec`减少创建开销，但需要重新设计Session卷归属、后台进程和恢复；短命预热沿用每调用独立容器，改动更小，本轮采用后者。启动检查不能替代实际命令前的lease/fence、审核和权限校验，因为Docker、Session和Run状态随后都可能变化。取消启动时也要等待资源清理，并继续传播取消状态。

小练习：不关闭Docker Desktop，仅把测试子进程的`DOCKER_HOST`指向不存在的socket，预测`init`和`serve`各自的退出结果，再解释为什么预热容器不能挂上所有Session工作卷。实际验证见BASH_STARTUP_REPORT.md。

## 2026-11-16：让启动过程可观察

镜像像可复用的程序包，容器像一次运行的进程；本地已有镜像时无需重复下载，短命容器结束后可自动删除。没有下载日志或常驻容器并不能判断是否执行成功。四阶段进度记录实际检查/复用或构建/预热/清理，等待秒数表示仍在处理，不是假设完成百分比。

日志级别可能过滤成功消息，管道也可能缓冲；固定启动提示使用stderr立即flush，实际HTTP监听使用Uvicorn就绪日志。两种方式是直接转发Docker详细日志，或显示受控阶段/耗时；后者能保持凭据和本机路径不进入日志，本轮采用。阶段结束要取消进度心跳，失败不能显示完成；沙箱成功、应用初始化和端口监听是不同状态。

小练习：说明为什么已经显示“沙箱准备完成”后仍可能因8000端口被占用而启动失败，以及为什么不应把四个阶段平均换算成25%/50%/75%下载进度。结果见BASH_STARTUP_PROGRESS_REPORT.md。

## 2026-11-17：从命令审核到能力边界

命令分类像后端请求校验，只能看到声明参数；任意Python可以编码、创建子进程和重定向，不能靠字符串白名单证明无害。实际边界像事务/网关权限：容器限制宿主访问，代理限制目标和操作，版本化工作区在批准前保留已确认文件，lease/fence阻止过期提交。

两种联网方式是内部网络加防火墙，或禁网容器通过Unix socket访问固定出口。本次用后者，让脚本没有绕过HTTP代理的IP/DNS通路。代理核验全部解析结果后连接固定IP，保留TLS域名校验；连接时再次按域名解析会留下重绑定窗口。Fake-IP应拒绝，由管理员明确选择可信解析，不将保留网段当公网。

COMMAND_TOO_LONG提示分块写脚本，EXECUTION_ERROR保留退出码与Python异常，NETWORK_DENIED表示能力边界。普通本地开发无需每次模型复核；模型不能授予权限。POST批准针对具体请求，响应丢失后重跑整个脚本可能重复前面的副作用。

恢复也影响配额：只记录成功返回次数会让代理崩溃后重置额度。先预留，封闭新请求后核销，无法核验时保留额度；这仍不保证远端Exactly-once。小练习：画出脚本→UDS→代理→API，标出Token与DNS所在层，解释响应丢失后哪些步骤能重试，以及工作区软监测为何不是卷硬配额。见BASH_EXECUTION_POLICY_GUIDE.md及报告。

## 2026-11-17：主题是偏好，Markdown 是展示

主题放在后端可同步设备，但要增加接口并处理离线；放在客户端简单且足以满足当前需求。因此用现有 Zustand 记录公开偏好、matchMedia 获取系统主题、CSS 变量统一配色，不把外观写进消息或命令权限。存储失效时仍能临时切换，显式浅/深不受系统变化覆盖。

Markdown 也有两种实现：手写有限语法，或使用成熟解析器。前者依赖少但难正确处理嵌套语法与边界，后者增加体积但能将文本转为可控 React 节点。本次选择后者，后端仍保存原文；HTML、图片自动请求、代码执行是不同能力，并不会因为支持 Markdown 就自动开放。

链接点击也跨信任边界：消息 URL 不等于可执行命令。Renderer 和 Main 都验证 HTTP/HTTPS，拒绝本地文件/脚本等协议；真正点击才交系统浏览器，不给消息 Node 或原生调用权限。单元测试验证纯规则，桌面测试验证真实 DOM、系统主题和窗口/外链处理；打包测试还要单独运行，不能只看构建成功。

小练习：切换浅色时观察会话 ID、草稿和命令权限是否变化；再用包含标题、代码块和远程图片的文本，解释为什么数据库保留 Markdown 标记，而窗口显示排版且不会自动下载图片。

## 2026-11-17：账户额度、生成预算与自动重试

账户可用额度决定能否消费；max_tokens限制一条请求生成的总量。实测HTTP200且2048全部是reasoning_tokens时，账户能完成调用，但模型仍没有最终正文。把所有空正文都归为“拒绝”会掩盖真实原因。固定合成输入的对照可隔离参数因素，再通过实际网关确认链路，不需要发送私人对话。

重试有两种办法：相同参数重新发送可应对瞬时抖动；针对预算不足调整有界参数才有机会解决确定性耗尽。都只能重试模型请求，不能重放已执行的工具，也不能绕过取消/总超时或在崩溃后无界重复付费。小练习：初次加三次重试总共几次请求？如果四次都给2048且都耗于思考，为何有余额仍然拿不到正文？

### 同日：把重试放在正确的边界

共享ModelGateway只重试HTTP模型请求，成功一次后才进入原Decision/Tool流程，所以网络抖动不会让已完成命令再次执行。初次加三次是四次尝试，但全部共用模型60秒或审核30秒；实测复杂思考耗尽60秒，说明“允许重试”不等于“延长总等待”。

ModelRetryPolicy提供可测纯规则与异步等待注入；故障消息只暴露安全代码，日志只暴露结束原因/计数/存在标志。用完整CSV合成任务真实验证了2048无正文→4096有正文，并同时记录复杂任务未完成的事实。小练习：在日志中按同一独立call标记找attempt/output_budget/outcome，解释为什么第三次read阶段的MODEL_TIMEOUT与第一次parse阶段的MODEL_OUTPUT_LIMIT要分别处理。
